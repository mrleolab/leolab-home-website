Physics, formulas & data sources +

Newton’s gravity

aᵢ = G Σⱼ≠ᵢ mⱼ (rⱼ − rᵢ) / |rⱼ − rᵢ|³

Every body attracts every other body. Velocity Verlet advances position and velocity with a fixed integration step; simulation rate controls how many days pass per second.

Kepler & orbital energy

T = 2π √(a³ / μ) · μ = G(M + m)

ε = v²/2 − μ/r and a = −μ/(2ε). The displayed period exists only for bound orbits. Changing mass or G preserves current velocity, then changes acceleration.

What the model represents

Distances use AU; velocities use km/s. Body sizes are enlarged for visibility. Initial elements are J2000 approximations (Earth represents the Earth–Moon barycenter). This educational model omits relativity and collision dynamics. Large energy drift signals that a smaller step is needed.

01 / COMPUTER SCIENCE

Build foundations.
Not just a toolset.

Connect what you code with how the system works.

+Read the note

A language is a starting point, not the whole picture. A useful learning question is: can I explain the data, the logic, and the decisions behind what I built?

Start with a small project, trace how information moves through it, and write down what you still need to understand. Then connect that question to the wider system: networks, databases, security, or the cloud.

02 / SCIENCE IN PRACTICE

Change gravity.
Question the orbit.

Turn a physics formula into an experiment you can observe.

+Read the note

In the Starfield Laboratory, increasing the Sun’s mass changes gravitational acceleration. It does not instantly assign a new velocity to a planet—the trajectory responds as the simulation advances.

Try it: pause the model, choose Earth, increase solar mass, then step forward. Compare the path, speed, and energy drift. Reset and repeat with a smaller integration step to see how numerical accuracy affects the experiment.

Try it in the laboratory ↗
03 / BUILDING WITH AI

Let AI explain.
Let tests verify.

Use an assistant to deepen understanding, not skip it.

+Read the note

When working with an AI coding tool, ask it to explain the approach, name its assumptions, and suggest a test before accepting a change. A confident answer is not the same as working software.

Keep the feedback loop small: read the code, run it, check an edge case, and explain the result in your own words. The most useful output is something you can understand and improve.
